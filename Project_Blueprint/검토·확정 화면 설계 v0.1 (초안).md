# 검토·확정 화면 설계 v0.1 (초안)

Nov 11, 2026 · 설계 문서 v0.3 "진행 단계 3. 검토·확정 화면"의 상세 설계

> **상태:** 설계만 한다. 설계 문서 v0.3에 따라 2단계(재현율 목표) 확정 전에는 구현하지 않는다. 2단계는 AI가 만든 정답 파일 기준으로 잠정 달성했다 (컬프 2023 세트 3순위 재현율 95.6%). 사람 검수 후 확정된다.

## 목적과 완료 조건

회사 SOP를 올리면 도구가 기본 템플릿 107건을 회사 조항에 연결한 초안을 낸다. 이 화면에서 사람이 초안을 하나씩 판정해 회사 버전 v1을 확정한다.

- **완료 조건 (v0.3 그대로):** 컬프 회사 버전 v1 확정.
- **설계 목표:** 검토자가 SOP 원문을 따로 열지 않고, 하루 안에 한 사람이 끝낼 수 있는 분량과 흐름. 목표치는 의무 1건당 평균 1분 이내 (첫 측정 후 다시 정한다).
- **원칙:** 도구의 판정(있음·확인 필요·없음)은 제안일 뿐이다. 모든 템플릿 의무는 사람의 결정을 거쳐야 확정된다. 확정 버전만 안내에 쓴다.

## 화면이 다룰 분량 (실측)

2026-11-11 매칭 규칙 기준. 240613 세트는 정답 파일이 없어 분포만 있다.

| 항목 | 컬프 2023 (SOP 29개) | 240613 (SOP 38개) | 설계에 주는 의미 |
| --- | --- | --- | --- |
| 템플릿 의무 | 107 | 107 | 모두 사람 결정 필요 |
| └ 도구 판정 "있음" | 38 | 39 | 일괄 승인 대상. 단, 1순위가 정답인 비율 23/26 (88%) |
| └ 도구 판정 "확인 필요" | 65 | 68 | 화면의 주 작업. 1~3순위에 정답 있음 39/42 |
| └ 도구 판정 "없음" | 4 | 0 | 빈틈 후보. 건수는 적지만 결과가 무거움 |
| 회사 고유 후보 (템플릿 후보에 안 걸린 의무형 문장, 강함) | 53 | 91 | SOP별로 묶어 빠르게 채택·제외. SOP당 최대 9건 |
| 회사 고유 후보 (보통) | 307 | 471 | 기본은 접어 둠. 필요한 사람만 펼침 |

이 표에서 나온 설계 결정 세 가지:

1. **"확인 필요"가 주 작업이다.** 화면의 기본 대기열은 "확인 필요"부터 시작하고, 1~3순위 후보 중 하나를 고르는 동작이 한 번의 키 입력으로 끝나야 한다.
2. **"있음"도 무조건 일괄 승인하지 않는다.** 1순위가 틀린 경우가 9건 중 1건꼴이다. 일괄 승인 목록에도 1순위 조항 본문 한 줄을 보여 주고, 2순위와 점수 차가 작으면 "후보 비슷함" 표시를 단다 (차이 기준은 구현 때 측정해 정한다).
3. **회사 고유 후보 "보통"은 기본으로 숨긴다.** 수백 건을 다 보이면 검토가 끝나지 않는다. 강함만 기본으로 보이고, 보통은 SOP별 "더 보기"로 둔다.

## 화면 흐름

```
업로드 ──▶ 검토 대기열 ──▶ 의무 판정 (반복) ──▶ 회사 고유 후보 ──▶ 확정
  │            │                                                      │
  파싱 결과    진행률·남은 건수                                       v1 생성
  즉시 표시    판정별·SOP별 묶음                                      확정자·일시 기록
```

검토는 여러 번에 나눠 해도 된다. 결정은 내릴 때마다 저장하고, 다시 열면 이어서 한다.

### 1. 업로드

v0.3과 같다. 파일과 SOP 세트 버전을 정하고, 파싱 결과(SOP 수, 조항 수, 서식 수, 경고)를 바로 보여 준다. 여기에 매칭 결과 요약(있음·확인 필요·없음 건수)을 더한다.

### 2. 검토 대기열

(판정별 건수는 컬프 2023 세트 실측, 결정·남은 건수는 예시다.)

```
┌───────────────────────────────────────────────────────────────────────┐
│ 컬프 SOP 2023 · 템플릿 107건 중 결정 41건 (38%)    [확정하러 가기 ▸] │
├───────────────────────────────────────────────────────────────────────┤
│ ▸ 확인 필요      65건 남음 24   ← 기본으로 여기서 시작              │
│ ▸ 없음 (빈틈)     4건 남음  4                                        │
│ ▸ 있음           38건 남음 38   [SOP별 일괄 승인]                    │
│ ▸ 회사 고유 후보 53건 남음 53   (보통 307건 숨김)                    │
│ ─────────────────────────────────────────────────────────────────── │
│ 묶어 보기: [판정별] SOP별   유형별      □ 보류한 것만                │
└───────────────────────────────────────────────────────────────────────┘
```

- **기본 순서:** 확인 필요 → 없음 → 있음 → 회사 고유 후보. 같은 판정 안에서는 SOP 번호순으로 둬서, 같은 SOP의 조항을 이어서 보게 한다 (원문 맥락을 다시 읽지 않아도 됨).
- **v0.3의 "플래그 먼저"와의 관계:** 기한 없음·모호한 표현 같은 플래그는 판정 안에서 앞에 세운다.

### 3. 의무 판정 (핵심 화면)

```
┌──────────────────────────────┬────────────────────────────────────────────┐
│ T071 · 수시 이벤트           │ 후보 조항                                  │
│ 트리거: QA 점검 부적합       │ ① CTM/004 5-2(10)   점수 0.43              │
│ 시정·재발방지 조치 기록 후   │   (요약) 기록감독자의 [시정] 요구를 받으면 │
│ 점검자 회신                  │   [시정]·[재발방지] [조치]를 문서로 남겨   │
│                              │   [회신]한다                               │
│ 도구 판정: 확인 필요         │   ▸ 상위: 5-2 시험책임자의 임무            │
│ 이유: 조항에 트리거 단어     │ ② CTM/004 5-5(10)   점수 0.24              │
│ (qa, 점검, 부적합)가 없음    │ ③ CTM/017 5.(3)3)  점수 0.19              │
│ 기한: (템플릿) 접수 시       │ ────────────────────────────────────────── │
│ 서식: 014-1                  │ 템플릿 근거 (컬프 2026 COM/014 6.(1))      │
│ 담당: 시험책임자             │   (요약) 시정·재발방지 조치를 기록해       │
│                              │   점검자에게 회신                          │
├──────────────────────────────┴────────────────────────────────────────────┤
│ [1][2][3] 이 조항으로 연결   [F] 다른 조항 찾기   [N] 회사 SOP에 없음     │
│ [X] 해당 없음(제외)   [H] 보류   메모: ________________                  │
└───────────────────────────────────────────────────────────────────────────┘
```

위 예는 컬프 2023 세트의 실제 매칭 결과다. 1순위 조항은 "기록감독자의 시정요구"에 대한 회신이라, 신뢰성보증(QA) 점검 부적합 회신과는 계기가 다르다. 2023 AI 정답 파일도 이 의무를 "없음"으로 봤다. 검토자는 상위 조항 제목과 템플릿 근거를 나란히 보고 N(회사 SOP에 없음)을 고르게 된다.

**왼쪽: 의무 카드.** 할 일, 트리거, 유형, 기한·서식·담당(템플릿 값), 도구 판정과 이유.

**오른쪽: 근거.**

- 후보 1~3순위 조항 원문. 공통 키워드·트리거 단어·서식 이름을 강조 표시한다 (매칭 결과의 `sharedKeywords`, `triggerHits`, `formHits`를 그대로 쓴다).
- 조항마다 상위 조항 제목을 한 줄로 보이고, 눌러서 같은 묶음의 앞뒤 조항을 펼친다. "정답이 바로 옆 조항"인 경우(예: 2023 세트 #17)를 여기서 잡는다.
- 템플릿 근거 원문을 함께 보여 준다. 비교 기준이 있어야 같은 의무인지 판단할 수 있다. (외부 배포 때는 이 원문을 지정규정 기준 문구로 바꿔야 한다. 설계 문서 v0.3 열린 질문)
- "없음" 판정이면 회사 SOP에 없는 핵심 단어(`missingKeywords`)를 보여 준다.

**결정 (한 번에 하나):**

| 결정 | 키 | 결과 | 비고 |
| --- | --- | --- | --- |
| 이 조항으로 연결 | 1·2·3 | 상태 → 검토됨. 근거 조항 = 고른 조항 | 여러 조항이 함께 정하면 Shift로 추가 선택 |
| 다른 조항 찾기 | F | 조항 검색 (SOP 번호·본문 글자) → 고르면 연결 | 후보 3개 밖에 정답이 있는 경우 |
| 회사 SOP에 없음 | N | 상태 → 검토됨, "회사 SOP에 없음"으로 기록 | 빈틈 점검 결과. 안내에 쓸지 따로 고름 (아래) |
| 해당 없음 (제외) | X | 상태 → 제외. 사유 필수 | 예: "병원체 시험을 하지 않음" |
| 보류 | H | 대기열 끝으로. 확정 전에 다시 나옴 | 담당자 확인이 필요한 경우 |

- 결정 후 자동으로 다음 항목으로 넘어간다. 마지막 결정은 되돌릴 수 있다 (Ctrl+Z).
- **"회사 SOP에 없음"인 의무를 어떻게 할지:** 두 가지 중 고른다. (1) 법령상 의무라 안내에는 넣는다 (근거를 "템플릿/지정규정"으로 표시하고 SOP 개정 필요 목록에 올림). (2) 안내에서 뺀다. 기본값은 (1)로 한다. 이 도구의 위험 1순위가 "있는 의무를 없다고 믿게 됨"이기 때문이다.

**연결 후 회사 값 확인 (같은 화면 아래쪽에 펼침):**

- 기한: 고른 조항에서 기한 문구가 추출되면(파이프라인 4단계) 템플릿 값과 나란히 보여 주고, 다르면 회사 값을 기본으로 한다. 다른 경우는 강조한다.
- 서식: 고른 조항이 언급한 회사 서식 코드(`formRefs`)를 기본값으로 채운다.
- 담당·보고처: 회사 직무 목록에서 고른다.
- v0.3 원칙대로 자유 입력은 "할 일" 설명에만 허용하고, 나머지는 선택 목록과 정해진 칸으로만 바꾼다.

### 4. "있음" SOP별 일괄 승인

```
CTM/001 SOP 및 서식의 작성 및 관리 · 있음 5건
 ☑ T018 소관 SOP 정기 검토 …     → 5-1(3) (요약) 작성 책임자의 정기 SOP 검토              0.42 / 0.26
 ☑ T060 일탈 기록 …              → 9.(1)  (요약) SOP 일탈 시 일탈기록지 작성              0.48 / 0.24
 ☑ T061 시험책임자 보고, 일탈 …  → 9.(1)  (요약) SOP 일탈 시 일탈기록지 작성              0.48 / 0.37
 ☐ T079 SOP 사용중단 처리 …      → 5-3(5) (요약) 개정 시 반납된 구판 사본 파쇄·원본 보관  0.44 / 0.40  ⚠ 후보 비슷함
 ☑ T105 효력정지 원본 보관 …     → 6-2(2) (요약) 효력 정지된 구판 원본 보관               0.49 / 0.39
                                              [체크한 4건 승인]  [하나씩 보기]
```

- 1순위 조항 본문 첫 줄과 1·2순위 점수를 반드시 보여 준다. (이 문서의 예시는 공개 저장소에 SOP 원문이 실리지 않도록 조항 내용을 요약으로 바꿔 적었다. 실제 화면은 원문을 보여 준다.) 줄만 읽고도 틀린 연결을 걸러낼 수 있게 한다.
- 위 예는 컬프 2023 세트의 실제 결과다. T079는 1순위가 개정 절차 조항(5-3(5))이고, 2023 AI 정답 파일 기준 맞는 조항은 "8. SOP의 사용중단" 아래에 있다. 1·2순위 점수 차가 0.04라 "후보 비슷함"으로 걸러진다. 반대로 T105도 차이가 0.10으로 작은 편이라, 기준값은 실제 검토 결과로 정해야 한다.
- "후보 비슷함" 표시가 있는 항목은 기본으로 체크를 끈다. 하나씩 보기로 넘긴다.

### 5. 회사 고유 후보

템플릿에 없는 회사 고유 의무 후보를 SOP별로 묶어 보여 준다. 결정은 "채택(의무 카드 새로 만듦)" 또는 "의무 아님"뿐이다. 채택하면 판정 화면과 같은 카드가 열려 유형·트리거·기한·서식·담당을 채운다 (template\_id 없음).

- 기본은 강함만 보인다. 보통은 SOP별 "더 보기".
- 한 SOP의 후보를 모두 "의무 아님"으로 하는 버튼을 둔다 (SOP 절차 설명만 있는 경우).

### 6. 확정

(건수는 화면 모양을 보이기 위한 예시다.)

```
회사 버전 v1 확정 · 컬프 SOP 2023
 연결됨 88 · 회사 SOP에 없음 6 (안내에 포함 5) · 제외 13 · 회사 고유 채택 7
 남은 것: 보류 0 · 미결정 0 · 기한 미정 플래그 3 (사유 입력됨 3)
 확정자: [시험실시기관장 ▾]                [v1 확정]
```

- 확정 조건: 미결정·보류 0건. 남은 플래그는 사유를 적어야 한다 (v0.3과 같음).
- 확정하면 그 시점의 결정 묶음을 바꿀 수 없는 스냅샷(v1)으로 저장하고, 확정자와 일시를 남긴다. 이후 수정은 v2를 만드는 일이다.
- 확정 때 함께 내보내는 것: (1) 회사 버전 파일(JSON), (2) 빈틈 보고서("회사 SOP에 없음" 목록과 SOP 개정 필요 목록), (3) 검토 결과를 정답 파일 형식으로 (아래 "검토 결과를 평가에 되돌리기").

## 데이터 모델 추가

v0.3의 Obligation 상태(초안·검토됨·확정·제외)는 그대로 쓰고, 사람의 결정 이력을 따로 남긴다.

| 엔터티 | 핵심 필드 | 비고 |
| --- | --- | --- |
| ReviewSession | SopSet, 템플릿 이름·버전, 매칭 규칙 설정값(스냅샷), 시작일 | 어떤 규칙으로 만든 초안을 검토했는지 남긴다 |
| ReviewDecision | 템플릿 의무 id (또는 회사 고유 후보 id), 결정 (연결·없음·제외·보류·채택·의무 아님), 연결 조항 id\[\] + 조항 해시, 바꾼 필드 값, 사유·메모, 결정자, 결정 시각, 그 당시 도구 판정·점수 | 덧붙이기만 한다. 되돌리기도 새 기록. 마지막 기록이 현재 결정 |
| CompanyVersion | 버전 번호, 확정자, 확정 일시, Obligation 스냅샷 | 확정 후 바꾸지 않는다 |

- **조항 해시를 함께 저장하는 이유:** 개정판을 올렸을 때(5단계) 해시가 바뀐 조항에 걸린 결정만 다시 초안으로 돌리기 위해서다.
- **도구 판정·점수를 함께 저장하는 이유:** "도구는 있음이라 했는데 사람이 없음으로 바꾼" 건을 모아 규칙 개선에 쓴다.

## 저장

v0.3의 저장 설계(IndexedDB + 파일 자동 저장)는 4단계 범위다. 3단계에는 최소한 다음이 필요하다. 검토가 하루 이상 걸릴 수 있고, 결정이 사라지면 다시 할 수 없기 때문이다.

- 결정할 때마다 IndexedDB에 저장한다.
- "검토 내보내기·가져오기" (JSON)를 둔다. 다른 PC에서 이어서 하거나 백업할 때 쓴다.
- 파일 자동 저장(File System Access API)은 4단계에서 붙인다. 붙이기 전까지는 첫 화면에 "아직 파일로 저장되지 않음, 내보내기를 권함" 안내를 띄운다.

## 검토 결과를 평가에 되돌리기

검토 화면에서 내린 결정은 그 자체가 사람이 검수한 정답이다. 결정을 `scripts/score-template-match.ts`가 읽는 정답 파일 형식(템플릿 번호, 정답 조항, 확신, 근거)으로 내보내면:

- 매칭 규칙을 바꿀 때마다 실제 회사 결정으로 재현율을 다시 잰다 (지금은 AI가 만든 정답 파일만 있음).
- 회사가 늘수록 정답 세트가 늘어, 과적합을 검사할 데이터가 생긴다.

연결은 "정답 조항", 회사 SOP에 없음은 "없음", 제외는 정답 파일에서 뺀다 (회사 사정이지 매칭 문제가 아님). 확신은 "높음"으로, 보류 후 결정한 것은 "중간"으로 적는다.

## 구현 순서 (2단계 확정 후)

1. 검토 상태 저장 (ReviewSession·ReviewDecision, IndexedDB, 내보내기·가져오기). 화면보다 먼저 만들고 테스트한다.
2. 의무 판정 화면 (대기열 + 카드 + 후보 근거 + 키 입력). 여기까지로 실제 검토를 시작할 수 있다.
3. 정답 파일 내보내기. 2023 세트를 이 화면으로 검토해 정답 파일을 사람 검수본으로 바꾼다.
4. "있음" 일괄 승인, 회사 고유 후보 화면.
5. 연결 후 회사 값 확인 (기한·서식·담당).
6. 확정과 스냅샷, 빈틈 보고서 내보내기.

## 측정

- 의무 1건당 평균 결정 시간, 대기열별 소요 시간 (결정 시각 차이로 계산).
- 도구 판정과 사람 결정의 불일치 표 (특히 "있음"→다른 조항, "없음"→연결).
- 일괄 승인 후 다시 고친 비율. 높으면 일괄 승인 조건을 조인다.

## 열린 질문

- [ ] **검토 화면을 2단계 확정 전에 먼저 만들지.** 지금 2단계를 막고 있는 것은 정답 파일 검수(사람 일)이고, 검토 화면의 1~3번 구현이 바로 그 검수 도구가 된다. 엑셀로 검수하는 것보다 빠르다면 순서를 바꿀 이유가 된다. 설계 문서 v0.3의 "미달이면 화면 개발로 넘어가지 않는다"는 원칙과 부딪히므로 결정이 필요하다.
- [ ] 확정 권한 (v0.3 열린 질문 그대로): 시험실시기관장만, 또는 SOP 작성 책임자별. 책임자별이면 SOP별로 나눠 확정하는 흐름이 필요하다.
- [ ] "회사 SOP에 없음"인 의무의 기본값을 "안내에 포함"으로 둘지 (이 설계의 제안), 매번 고르게 할지.
- [ ] 일괄 승인의 "후보 비슷함" 기준 (1·2순위 점수 차). 2023 세트 검토 결과로 정한다.
- [ ] 검토자가 여러 명일 때: 공유 폴더 한 파일로 나눠 하면 동시 저장 문제가 생긴다 (v0.3 위험 표). 첫 버전은 한 사람이 검토하는 것으로 가정한다.
